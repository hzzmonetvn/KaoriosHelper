# Native configuration decisions

## Core synchronization and runtime identity — 2026-11-14

### Situation and approach

The native control interface already owned module configuration, but Settings.Global synchronization, crash recovery and producer-generation linkage were incomplete. Python compatibility status also interpreted weaker ACK evidence independently. Keep one production control ingress: native `helperctl`, on demand, without a daemon or Settings watcher. Persist requested state separately from evidence of runtime initialization and physical-device verification.

### Implemented choices

1. **Use source-derived, allowlisted Settings.Global adapters.** Execute `/system/bin/settings get global KEY` with direct arguments, never shell interpolation. Capture selected keys twice within one 30-second deadline; reject differing reads. Limit each value to 16 MiB and the first snapshot to 32 MiB. Discard subprocess diagnostics and use fixed errors rather than exposing payloads. The two reads detect changes; they are not a provider-level atomic snapshot and do not rule out every ABA change.
2. **Keep explicit replacement distinct from synchronization merge.** `config set` replaces the entire validated payload, including deliberate removal of omitted fields. Settings adapters update supplied fields while retaining omitted manual fields and unrelated profiles. Missing, empty or literal `null` Settings values do not delete existing configuration. Semantically unchanged JSON does not advance generation. TEE compares exact payload bytes.
3. **Reject unsupported schema semantics before publication.** PIF supports JSON or property text. COPG converts supported GameProps fields to the existing native profile schema and preserves manual profile controls. HMA accepts scope arrays or an explicitly representable simple blacklist rule subset; rich framework rules, including normal defaults with WebView protection, are not full-parity conversions. TEE reads only the active `kaorios_keybox_xml`; structural acceptance is not complete XML or cryptographic validation. Kaorios scalar storage has no implemented runtime backend. The literal allowlists and mappings live in `core/config/settings_adapter.hpp`; no Secure-only or alternate-profile fallback is inferred.
4. **Prevalidate batches, then publish a recoverable native transaction.** Set, rollback, sync, migration, toggle, reload and boot-request preparation use one descriptor-pinned `NativeStore` and the shared `.config.lock`. Stage payload, validated LKG, generations, request identity, verification invalidation and relevant markers together. A durable `.native-transaction.json` redo journal is the commit decision. Every cooperating native management/snapshot reader recovers it under the lock before reading. Replaying replacements/removals is idempotent; delete the journal last.
5. **State the transaction guarantee precisely.** Individual replacements use exclusive private staging, file fsync, rename and directory fsync. Internal leaves require effective-UID ownership, regular-file/single-link checks, no group/world write access and no-follow descriptor-relative operations. Recovery validates journal shape and target allowlists; it does not rerun every engine schema validator. A failed command after journal publication can have an unconfirmed outcome that a later locked access completes. Arbitrary unlocked readers can observe intermediate multi-file state, so `atomicMultiFileSnapshot` remains false. Trusted ancestor paths are still required. Interrupted staging can leave unused staging files.
6. **Keep native generations explicit and per engine.** Configuration publication and rollback advance `ENGINE.stored_gen`; the request carries the same positive generation. Payload presence never invents generation 1. `config migrate ENGINE|all` validates legacy payloads and preserves exact bytes, creating native identity only for generation-zero payloads. COPG can copy legacy `COPG.json` into canonical `spoof.json` without deleting the original. Reload and enable/disable renew request identity without incrementing stored generation.
7. **Bind requests to a boot and a fresh token.** `ENGINE.request.json` holds a 128-bit random hexadecimal `requestId`, current boot UUID and `CLOCK_BOOTTIME` `notBeforeMillis`. Same-generation reload invalidates previous ACKs. `post-fs-data.sh` runs `prepare-boot` before Zygote consumption: valid current-boot requests remain stable, stale/malformed requests are renewed without generation inflation, and legacy configuration still needs explicit migration. Invalid managed configuration fails boot preparation rather than receiving a fabricated request.
8. **Require ACK v2 identity, not generation alone.** Mandatory typed/ranged fields bind engine, positive generation, SHA-256 of exact configuration bytes, request token, boot UUID, PID, effective UID, process start ticks, actual argv0 and bounded boot-time timestamp. Reject duplicate JSON keys, excessive nesting, malformed events, dead/zombie processes, PID reuse and mismatched identity. ACK v1 remains diagnostic only. Local ACK identity is not authentication against root or a compromised engine, and no arbitrary TTL expires an otherwise-live process.
9. **Publish monotonic process evidence.** Serialize ACK publication, reject duplicate/regressive events, and keep failure terminal within the same process/request/snapshot. A fresh valid request/process/snapshot can start progression again. The companion checks kernel peer credentials and current locked config/request identity; it never upgrades producer PID, generation, timestamp or configuration hash. The compatibility ACK alias references the same staged inode; its two renames are not claimed crash-atomic.
10. **ACK the snapshot actually supplied to the consumer.** HMA/PIF/COPG retain the payload bytes and corresponding generation/request metadata captured for initialization or profile selection. Later disk changes do not relabel an older applied snapshot. Legacy/unbound snapshots emit no current config-bound ACK. HMA's no-argument compatibility entrypoint does not prove that a particular configuration was supplied. No additional hook, concealment, attestation or secure-content functionality is introduced by this identity work.
11. **Read native status from one recovered locked view.** Runtime identity matches alone do not prove initialization. Applied state additionally requires `initResult == 0`, `errorCode == 0` and a successful initialization/observation event. Clear current process/hook/applied evidence when identity no longer matches; retain old event/time only as diagnostics. `READY` means initialized, `DEVICE_UNVERIFIED` means current observation without external device proof. Missing backends remain `INCOMPLETE_RUNTIME`. `deviceVerified` is false and legacy verification markers are not evidence.
12. **Delegate Python runtime/status compatibility to native control.** Fixed-argv calls use the installed `helperctl.sh` by default, with an explicit caller-injected control path used by integration tests. Require control/status protocol 1 and ACK-v2/recoverable-transaction capabilities. Missing, incompatible or failing control returns unavailable state with zero applied evidence; no raw-ACK, marker-write or cache fallback exists. `trigger_reload()` means request accepted, not applied. Reports preserve native wire fields; old version/root-mode arguments do not overwrite native identity. The optional private status cache is output only.
13. **Keep legacy Python persistence separate.** `ConfigManager` uses the same writer lock, its own `.config.transaction` recovery journal, validated `.last_known_good` backup and legacy global `generation.txt`. A published-but-unconfirmed operation reports generation -1 and recovers on a later access. This counter and journal do not interoperate with native per-engine metadata/journals. Native control remains the production configuration ingress; external raw readers and legacy Python writers do not gain native snapshot guarantees.
14. **Use existing lifecycle entrypoints.** Root-manager Action runs `config sync all` and then status, propagating sync failure. Boot prepares current request identities. Service remains a one-shot status query. None is a polling loop or a global boot-property mutation.

### Alternatives not chosen

- A daemon, Settings polling or shell-based payload transport would add lifecycle complexity or quoting exposure without being required for on-demand synchronization.
- Recursive merge for `config set` would prevent deliberate field removal; merge belongs only to owned Settings adapter fields.
- Silent conversion of unrepresentable HMA/COPG semantics would lose policy. An invalid member of `sync all` therefore rejects the whole batch before publication; callers can select a supported engine explicitly.
- Treating individual renames as an atomic multi-file snapshot would overstate what unlocked readers observe. A redo journal plus cooperating reader lock provides recoverability, not that guarantee.
- Relaxing identity to generation-only ACKs, restamping old producer evidence, or reusing a same-generation request would allow stale evidence to become current.
- Adding a second Python evidence interpreter would preserve two different definitions of applied state. The compatibility layer delegates instead.
- Reporting compilation, local readiness, DEX loading or an ACK as physical-device verification would invent evidence. No release gate is weakened or marked accepted without its required review.

### Remaining limitations and backend work

- Settings capture is not an Android provider transaction. Actual root-manager settings permissions, boot ordering, SELinux/proc visibility and app-to-module calls need device validation.
- Full framework HMA policy parity and Android ART behavior remain incomplete; COPG has host metadata tests, not verified device behavior.
- Kaorios and TEE runtime backends remain incomplete. ScreenCapture remains unsupported/disabled with a source-free declaration; no functioning native port is claimed.
- `config get` returns raw payloads. `redactedConfigRead`, structured mutation errors, device verification and arbitrary-reader multi-file atomicity remain false capabilities.
- Native final-directory/leaf protection does not protect every ancestor. Legacy status-cache/verification-clear helpers retain older direct-path implementation and are not production configuration ingress.
- Python compatibility configuration uses a different validation/generation domain; no common cross-language recovery transaction is claimed.
- Dependency/license acceptance remains independently gated. Diagnostic ZIPs are not release-qualified merely because CI builds them.
